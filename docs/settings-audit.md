# ตรวจค่าที่ยังฝังในโค้ด (settings audit)

กฎของโปรเจกต์นี้: **กฎธุรกิจต้องตั้งได้รายบริษัท ห้าม hard code** เพราะ Smartboss
ขายหลายบริษัท และแต่ละที่มีมาตรฐานคนละแบบ ค่าคงที่ในโค้ดที่เหลือไว้ได้มีอย่างเดียว
คือ **ค่าเริ่มต้นของบริษัทที่ยังไม่เคยตั้ง** และต้องเขียนกำกับว่าห้ามอ่านไปใช้ตรง ๆ

ไฟล์นี้คือรายการที่ตรวจแล้ว ณ 2026-08-08 — อัปเดตทุกครั้งที่ย้ายค่าไหนออกจากโค้ด

## ❗ ยังฝังอยู่ — เรียงตามความสำคัญ

### 1. นโยบายการเข้าสู่ระบบ · `apps/web/app/api/auth/login/route.ts`

| ค่า | ที่อยู่ | ตอนนี้ |
|---|---|---|
| ล็อกบัญชีเมื่อรหัสผิดกี่ครั้ง | `MAX_FAILED` บรรทัด 19 | 5 |
| ล็อกนานกี่นาที | `LOCK_MINUTES` บรรทัด 20 | 15 |
| ความยาวรหัสผ่านขั้นต่ำ | `admin/actions.ts:82, 257` | 8 |
| อายุ session | `ACCESS_TOKEN_TTL` / `REFRESH_TOKEN_TTL` (env) | 15m / 7d |

**ทำไมต้องแยกรายบริษัท**: บริษัทที่มีข้อมูลเงินเดือนอ่อนไหวอยากล็อกที่ 3 ครั้ง
และบังคับรหัสผ่าน 12 ตัว ส่วนบริษัทที่ให้ช่างภาคสนามใช้บนมือถืออยากผ่อนกว่านั้น
อายุ session ตอนนี้เป็น env ⇒ **ทั้งแพลตฟอร์มถูกบังคับให้เท่ากันหมด**

**เสนอ**: ตาราง `core.security_settings` — `maxFailedLogins`, `lockMinutes`,
`passwordMinLength`, `passwordRequireMixedCase`, `sessionIdleMinutes`,
`refreshTokenDays` · หน้าจอ `/admin/security`

> ⚠ `ACCESS_TOKEN_TTL` ย้ายเข้า DB ต้องระวัง: token ที่ออกไปแล้วอายุตามค่าเดิม
> การลดค่าไม่ตัด session ที่ค้างอยู่ ต้อง revoke refresh token ควบคู่

### 2. การแจ้งเตือนของโมดูลซ่อมบำรุง · `apps/web/modules/maintenance/data/cron.ts`

| ค่า | ที่อยู่ | ตอนนี้ |
|---|---|---|
| แจ้งเตือน PM ล่วงหน้ากี่วัน | `notifyDuePmSchedules` บรรทัด 69 | 7 วัน |
| เตือนใบงานที่ยังไม่บันทึกค่าใช้จ่าย หลังปิดงานกี่วัน | `notifyMissingExpenses` | **ไม่มีการผ่อนผันเลย** — ปิดงานปุ๊บเตือนปั๊บ |
| แสดงรายการในข้อความเตือนกี่บรรทัด | `.slice(0, 10)` | 10 |
| เวลาที่ส่งแจ้งเตือน | crontab ของเครื่อง | 08:00 |

**ทำไมต้องแยกรายบริษัท**: บ้านพักตากอากาศที่ต้องสั่งอะไหล่ล่วงหน้าอยากรู้ก่อน 30 วัน
ส่วนออฟฟิศที่ล้างแอร์เองรู้ก่อน 3 วันก็พอ · การเตือนเรื่องค่าใช้จ่ายทันทีที่ปิดงาน
คือการรบกวนช่างที่ยังไม่มีใบเสร็จในมือ

**เสนอ**: ตาราง `maintenance.notification_settings` — `pmLeadDays`,
`expenseGraceDays`, `maxItemsPerMessage`, `dailyDigestHour` · หน้าจอเพิ่มใน
`/maintenance/settings` ที่มีอยู่แล้ว

### 3. ช่วงเวลาของปฏิทินและรายงาน

| ค่า | ที่อยู่ | ตอนนี้ |
|---|---|---|
| ช่วงที่ปฏิทินโหลดมา | `app/api/report-task/store/[key]/route.ts` `defaultRange()` | −6 / +12 เดือน |
| ตัวเลือกช่วงเวลาหน้าสรุปผลงาน | `admin/performance/page.tsx` `RANGES` | 30 / 90 / 365 วัน |
| อายุ presigned URL ของไฟล์แนบ | `maintenance/lib/storage.ts` `SIGNED_URL_TTL_SECONDS` | 300 วินาที |

**ความสำคัญต่ำกว่าสองข้อบน** — ไม่ใช่ "กฎธุรกิจ" ที่เปลี่ยนผลลัพธ์ แต่เป็นการนำเสนอ
ยกเว้นอายุ presigned URL ที่เป็นเรื่องความปลอดภัย (ยาวขึ้น = ลิงก์ที่หลุดใช้ได้นานขึ้น)

**เสนอ**: ทำหลังสองข้อบน หรือรับเป็น query param แทนการเก็บลง DB

### 4. ค่าระดับแพลตฟอร์ม — **ไม่ต้องแยกรายบริษัท**

ค่าเหล่านี้ตั้งใจให้เป็นค่าเดียวทั้งระบบ ไม่นับเป็นของค้าง

| ค่า | เหตุผล |
|---|---|
| `GATEWAY_RATE_LIMIT` | ป้องกันโครงสร้างพื้นฐาน ไม่ใช่นโยบายบริษัท |
| `DEVICE_REQUEST_TIMESTAMP_TOLERANCE_SECONDS` | ความปลอดภัยของโปรโตคอล ผ่อนให้บริษัทเดียว = เปิดช่อง replay |
| `MAX_BODY_BYTES`, `HTTP_BODY_LIMIT_BYTES` | ขอบเขตของเครื่อง |
| `DEFAULT_TIME_ZONE`, `DEFAULT_CURRENCY` | ค่าตั้งต้นระดับ deployment (ตั้งได้ทาง env อยู่แล้ว) |
| อัตราประกันสังคม / ภาษี | **กฎหมาย** ไม่ใช่นโยบายบริษัท — อยู่ใน rule set ของ workforce แล้ว |

## ลำดับที่แนะนำ

1. **ขึ้นระบบก่อน** ด้วยโค้ดปัจจุบัน ([`docs/deploy.md`](deploy.md))
   ค่าที่ค้างอยู่ทั้งหมดมีค่าเริ่มต้นที่ใช้งานได้จริง ไม่มีอะไรพัง
2. ข้อ 1 (นโยบาย login) — กระทบความปลอดภัย และลูกค้าองค์กรมักถามข้อนี้ตอนประเมิน
3. ข้อ 2 (แจ้งเตือนซ่อมบำรุง) — กระทบประสบการณ์ใช้งานรายวันมากที่สุด
4. ข้อ 3 — เมื่อมีคนขอ

แต่ละข้อคือ migration + ตาราง settings + หน้าจอ + จุดอ่านค่า **ห้ามลืม**: จุดที่อ่านค่า
ต้องเรียกฟังก์ชัน `load…Settings(orgId)` เสมอ ห้ามอ่าน `DEFAULT_*` ไปใช้ตรง ๆ
และงานกวาดที่วิ่งข้ามบริษัทต้อง query ด้วยเกณฑ์ที่หลวมที่สุดก่อนแล้วค่อยกรองรายบริษัท
(ดูตัวอย่างที่ `dockOverdueMaintenance` ใน `modules/maintenance/data/cron.ts`)
